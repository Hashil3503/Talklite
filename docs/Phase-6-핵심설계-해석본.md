# Phase 6 핵심 설계 해석본 및 용어 사전

> 대상 문서: `Talklite-Phase-6-실행계획.md`  
> 프로젝트: Talklite (온디맨드 파티 매칭 & 오픈 보이스 플랫폼)  
> 목적: Phase 6(Room GC, MariaDB 영속화, 2중 동시성 가드, 종합 품질 보증)의 핵심 아키텍처와 설계 결정 이유를 비개발자 및 동료 개발자 모두가 쉽게 이해할 수 있도록 해설합니다.

## 1. Phase 6 핵심 아키텍처 해석

### 1) 왜 휘발성 방은 마지막 인원이 나갈 때 즉시 지워야 할까요? (Room GC)
* **배경**: Talklite는 게임 파티를 위한 즉석 매칭 플랫폼입니다. 파티가 끝나 모든 유저가 나가면 그 방은 더 이상 존재할 이유가 없습니다.
* **해결책**: 마지막 유저가 퇴장하는 순간, Redis 메모리에 있던 방 정보, 멤버 목록, 초대코드, 그리고 검색용 색인(게임명, 태그)을 남김없이 일괄 삭제합니다. 이를 통해 **서버 메모리 낭비를 원천 차단**하고, 로비 목록에서도 방이 즉시 사라집니다.

### 2) 마지막 사람이 나가는 순간 다른 사람이 들어오면 어떻게 되나요? (2중 상호 배제 가드)
* **문제 상황 (레이스 컨디션)**:
  * 유저 A가 "마지막으로 나가면서 방을 지우려는 순간", 유저 B가 "초대코드나 검색으로 방에 들어오려는 경우"가 발생할 수 있습니다.
  * 이때 방이 지워지면 B는 유령 방에 갇히게 되고, 반대로 B가 들어왔는데 방이 지워지면 B의 데이터만 찌꺼기처럼 남을 수 있습니다.
* **해결책 (2중 가드)**:
  * **가드 1 (`gc.lua`)**: 방을 지우기 직전, 방에 멤버가 0명인지 다시 확인합니다. B가 먼저 들어왔다면 방 삭제를 취소하고 방을 보존합니다.
  * **가드 2 (`join.lua`)**: 방에 들어갈 때 방 정보(meta)가 아직 존재하는지 먼저 확인합니다. 이미 A에 의해 방이 지워졌다면 입장을 거부하고 "존재하지 않는 방(404)"으로 안내합니다.

### 3) 영구 방은 서버가 꺼졌다 켜져도 어떻게 살아남나요? (MariaDB 영속화 & Re-hydration)
* **배경**: 영구 방(`PERMANENT`)은 사람이 아무도 없어도 계속 유지되어야 하는 클랜/고정 파티 방입니다. 하지만 Redis는 메모리 기반이라 서버 재시작 시 데이터가 사라질 수 있습니다.
* **해결책**:
  * 영구 방이 생성되거나 방장이 바뀔 때 MariaDB(`permanent_room` 테이블)에 안전하게 저장합니다.
  * 서버가 재부팅되면 `RoomRehydrator`가 MariaDB에서 영구 방 목록을 읽어와 **인원수 0명의 대기 상태 방**으로 Redis에 다시 복원(Re-hydration)시킵니다.

### 4) 왜 JPA 대신 `JdbcClient`를 썼을까요?
* Talklite의 영구 방 관리는 단 하나의 테이블(`permanent_room`)에 저장/조회/삭제하는 매우 명확하고 단순한 연산만 필요합니다.
* 복잡하고 무거운 JPA(Hibernate) 엔티티 생명주기 관리 대신, Spring 6의 가볍고 직관적인 `JdbcClient`를 사용하여 **성능을 최적화하고 코드 복잡성을 최소화**했습니다.

## 2. Phase 6 핵심 용어 사전

| 용어 | 쉬운 설명 | Talklite에서의 역할 |
| :--- | :--- | :--- |
| **Room GC (Garbage Collection)** | 쓰지 않는 메모리나 방을 자동으로 청소하여 회수하는 작업 | 휘발성 방의 인원이 0명이 되는 순간 Redis 키와 검색 역색인을 일괄 삭제하여 리소스를 회수함. |
| **Re-hydration (재수화/복원)** | DB 등에 건조하게 저장된 데이터를 메모리로 다시 불러와 활성화하는 과정 | 서버 재부팅 시 MariaDB의 영구 방 데이터를 Redis 메모리로 읽어와 0명 방으로 로비에 즉시 복구함. |
| **Race Condition (경합 상태)** | 여러 작업이 동시에 일어나 순서에 따라 예상치 못한 오류가 발생하는 현상 | 마지막 퇴장(GC)과 신규 입장(Join)이 동시에 일어날 때 방이 비정상 파기되거나 찌꺼기 키가 생기는 것을 방지함. |
| **2중 상호 배제 가드 (Mutual Exclusion Guard)** | 두 작업이 서로 충돌하지 않도록 양쪽에서 2중으로 검사하는 방어선 | `gc.lua`(멤버 0명 확인)와 `join.lua`(방 메타 존재 확인)가 맞물려 동시성 충돌을 원천 차단함. |
| **JdbcClient** | Spring Boot 3에서 제공하는 최신 데이터베이스 직접 조작 도구 | MariaDB `permanent_room` 테이블에 SQL을 명시적이고 빠르게 실행하는 영속화 계층. |
| **ROOM_REMOVED** | 로비에 방이 삭제되었음을 알리는 실시간 브로드캐스트 이벤트 | 방이 GC로 파기되었을 때 로비 유저들의 화면에서 해당 방 카드가 즉시 사라지게 함. |
| **Non-blocking SCAN** | Redis 서버를 멈추지 않고 패턴에 맞는 키를 조금씩 안전하게 탐색하는 방식 | 임시 밴 키(`room:{id}:banned:*`)를 서버 부하 없이 안전하게 청소함. |
