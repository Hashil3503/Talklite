## 👥 1. 2-Tab / 4-Pane 에이전트 전담 역할 정의

4개 Pane은 한 화면에 동시에 표시하지 않고, 다음과 같이 2개 Tab으로 나누어 운영합니다.

- **Tab 1 — 감독·검토**: `supervisor`, `reviewer`
- **Tab 2 — 구현·보완**: `implementer`, `refiner`

| Tab | Pane Label (식별 라벨) | Pane 위치 | Agent Kind | 적용 모델 (Designated Model) | 담당 역할 | 핵심 책무 및 위키 산출물 (Core Responsibilities & Artifacts) |
| :---: | :--- | :---: | :---: | :---: | :---: | :--- |

| 2 | **`refiner`** | 우 | `opencode` | **Muse Spark 1.3 Contributor**<br>(Provider: `OpenCode Go`) | **✨ 보완 작업<br>(Refiner)** | • **[사전 보완] `reviewer`의 사전검토 보고서(`reviews/Talklite-Phase-X-사전검토.md`)를 직접 정독하고 핵심설계 해석본(`designs/Talklite-Phase-X-핵심설계-해석본.md`) 작성**<br>• **[사후 보완] `reviewer`가 작성한 위키 검토 보고서(`reviews/Talklite-Phase-X-사후검토.md`)를 직접 정독하고 실제 코드 수정 및 보완 작업 전담 수행**<br>• **별도의 보완보고서를 생성하지 않고, 위키 `reviews/Talklite-Phase-X-사후검토.md` 하단에 `## 🛠️ 리파이너 보완 조치 및 최종 반영 내역` 섹션으로 실제 조치 내역과 빌드/린트 결과를 누적 덧붙임(Append-Only)**<br>• 브라우저 호환성 및 엣지 케이스 방어 가드 코드 적용<br>• 린트 0 error 및 빌드 무결성 유지 상태로 감독(`supervisor`)에게 인계 |

> [!CAUTION]
> **🚫 슈퍼바이저 직접 코드 구현 절대 금지 (Absolute Prohibition)**
> * `supervisor`는 **어떠한 경우에도 소스코드를 직접 작성·수정·삭제·리팩토링해서는 안 됩니다.**
> * 허용 행위: 태스크 지시(`orca terminal send`), 위키 문서 작성(`plans/`·`designs/`·`reports/`), 단계별 품질 게이트 승인, 읽기 전용 검증(`orca terminal read`, `git diff` 열람, `npm run lint`/`npm run build`/`mvn test` 결과 확인), Git 로컬 커밋 총괄.
> * 금지 행위: 에디터·`Edit`·`Write` 도구 등으로 프로젝트 소스코드 파일을 직접 변경하는 모든 행위.
> * 코드 변경 필요 시: 반드시 `implementer`(신규 구현) 또는 `refiner`(보완 수정)에게 `orca terminal send`로 지시하고, 완료 후 diff·빌드 결과로만 검증합니다.
> * 위반 시: 해당 Phase 품질 게이트 미통과 처리하며, 직접 수정분은 원복 후 정식 7단계 사이클(Step 4 또는 Step 6)로 재지시합니다.

## 🔄 2. 마일스톤 표준 7단계 개발 사이클 (Standard Lifecycle)

모든 마일스톤은 아래 **7단계 순환 프로세스**를 엄격히 준수하여 순차적으로 진행합니다.

```mermaid
graph TD
    S1["1단계: 계획서 확인 (supervisor)"] --> S2["2단계: 사전 검토 (reviewer)"]
    S2 --> S3["3단계: 사전 설계 보완 & 해석본 확정 (refiner → supervisor)"]
    S3 --> S4["4단계: 구현 시작 (implementer)"]
    S4 --> S5["5단계: 사후 검토 (reviewer)"]
    S5 --> S6["6단계: 사후 보완 & 보고서 통합 (refiner)"]
    S6 --> S7["7단계: 최종 승인 & 위키 동기화 (supervisor)"]
    S7 -->|다음 Phase 진입| S1
```

---

### 📌 Step 1: 계획서 확인 (Plan Verification)
* **주관**: `supervisor` (총괄 감독, Tab 1 좌) *(※ 슈퍼바이저는 직접 코드 구현 절대 금지 — 지시·승인·문서 작성·읽기 전용 검증만 수행)*
* **수행 내용**:
  1. 위키 내 해당 Phase 실행 계획서 (**`plans/Talklite-Phase-X-실행계획.md`**) 및 핵심설계 해석본 (**`designs/Talklite-Phase-X-핵심설계-해석본.md`**) 정독 및 작성
  2. 선행 마일스톤과의 의존성 및 백엔드/프론트엔드 변경 영향도 파악
  3. 완료 정의(DoD) 및 테스트 요구사항 목록 확정

### 📌 Step 2: 사전 설계 검토 (Pre-Implementation Review)
* **주관**: `reviewer` (Tab 1 우)  *(※ 리뷰어는 검토만 전담)*
* **수행 내용**:
  1. `supervisor`가 `reviewer`에게 위키 실행 계획서 및 핵심설계 해석본에 대한 사전 설계 검토 요청
  2. 아키텍처 결함, 브라우저 API 제약사항, WebRTC/STOMP 충돌 가능성, 성능 병목 사전 도출
  3. 위키 **`reviews/Talklite-Phase-X-사전검토.md`** 파일로 상세 분석 보고서 직접 작성 및 저장 (코드 수정 일체 금지)

### 📌 Step 3: 사전 설계 보완 및 해석본 확정 (Pre-Implementation Refinement)
* **주관**: `refiner` → `supervisor` (Tab 2 우 → Tab 1 좌) *(※ 슈퍼바이저는 해석본 승인·확정만 수행하며 직접 코드 구현 절대 금지)*
* **수행 내용**:
  1. `reviewer`가 작성한 위키 사전검토 문서(`reviews/Talklite-Phase-X-사전검토.md`)를 직접 정독하고 지적 사항별 해결책, 스키마 패치, 상태 머신 가드를 도출
  2. 핵심설계 해석본(`designs/Talklite-Phase-X-핵심설계-해석본.md`)을 작성하여 `supervisor`에게 확정 요청
  3. `supervisor`는 해석본을 최종 확인하고 실행 계획서 및 구현 규칙을 확정

### 📌 Step 4: 구현 시작 (Main Implementation)
* **주관**: `implementer` (메인 구현, Tab 2 좌)
* **수행 내용**:
  1. `supervisor`의 작업 지시에 따라 코어 비즈니스 로직, API, 컴포넌트, 상태 스토어 구현
  2. 로컬 린트 및 빌드 검증 수행 (`npm run lint`, `npm run build`, `mvn test-compile`)
  3. 변경 사항 목록 및 1차 구현 완료 보고서를 작성하여 `supervisor`에게 전달

### 📌 Step 5: 사후 검토 (Post-Implementation Review)
* **주관**: `reviewer` (코드 검토, Tab 1 우)  *(※ 리뷰어는 검토만 전담)*
* **수행 내용**:
  1. `git diff`를 정밀 분석하여 코드 품질, 잠재적 버그, 리소스 해제 누락, UI 접근성 점검 (코드 수정 금지)
  2. 수정이 필요한 구체적인 항목(P0/P1/P2 Action Items)과 파일 위치, 라인 번호, 개선 가이드를 위키 **`reviews/Talklite-Phase-X-사후검토.md`** 파일로 직접 작성하여 저장
  3. **⚠️ [누적 기록(Append-Only) 원칙]**: 추가 이슈나 재검토가 발생할 때 **절대로 기존 보고서 내용을 덮어쓰지 않고, `## [Round 1] 1차 사후 검토`, `## [Round 2] 2차 긴급 검토` 등 하단에 누적(Append)하여 이전 발견 내역과 히스토리를 100% 영구 보존**합니다.

### 📌 Step 6: 사후 보완 & 보고서 통합 (Post-Implementation Polish & Merge)
* **주관**: `refiner` (보완 작업, Tab 2 우)  *(※ 리파이너는 보완 코드 작성 전담)*
* **수행 내용**:
  1. `supervisor`로부터 검토 보고서 파일 경로를 전달받아, 위키 **`reviews/Talklite-Phase-X-사후검토.md` 문서를 직접 열람 및 정독**
  2. 보고서에 기술된 Action Items(P0/P1/P2)를 빠짐없이 실제 소스코드에 반영 (리팩토링, 엣지 케이스 가드 적용, 디바운스/핫스왑 최적화)
  3. **⚠️ [단일 통합 보고서 작성 규약]**: **별도의 보완보고서 파일을 생성하지 않고, 위키 `reviews/Talklite-Phase-X-사후검토.md` 하단에 `## 🛠️ 리파이너 보완 조치 및 최종 반영 내역` 섹션으로 실제 코드 수정 내역과 린트/빌드 결과를 덧붙여(Append-Only) 단일 통합 문서로 완성**합니다.
  4. 프론트엔드 린트 0 error 및 빌드 통과 재확인 후 `supervisor`에게 최종 인계

### 📌 Step 7: 최종 승인 및 다음 마일스톤 (Final Approval & Handoff)
* **주관**: `supervisor` (총괄 감독, Tab 1 좌) *(※ 슈퍼바이저는 직접 코드 구현 절대 금지 — 검증·승인·문서 동기화·커밋 총괄만 수행. 결함 발견 시 Step 4/Step 6로 재지시)*
* **수행 내용**:
  1. **품질 게이트 검증**:
     * 프론트엔드: `cd frontend; npm run lint && npm run build` (0 error)
     * 백엔드: `cd backend; .\mvnw.cmd test` (전체 회귀 테스트 ALL PASS)
  2. **위키 마일스톤 완료 보고서 작성**:
     * 위키 **`reports/Talklite-Phase-X-완료보고서.md` 작성**: 마일스톤 목표 및 달성 요약, 주요 구현 내용(Web Audio, API, UI 등), 품질 검증 결과 표(린트/빌드/테스트/DoD)를 간략하고 명확하게 작성
  3. **지식 베이스 및 문서 동기화**:

## 🖥️ 3. 세션 무관 2-Tab / 4-Pane 작업 환경 유지 지침 (Orca Environment Rule)

어떤 세션이나 재시작 상황에서도 **항상 동일하고 일관된 멀티 에이전트 작업 환경을 보장**하기 위해 다음 규정을 준수해야 합니다.

### 3.1 Tab 구성 및 패널 배치

4개 에이전트는 모두 **동일한 Orca 워크트리(`C:/Users/kimmh/VibeCoding/project/Talklite`, 셀렉터 `active`)** 안에서 실행합니다. 새로운 세션을 구성하거나 초기화할 때는 1번 탭에 `supervisor`(좌)와 `reviewer`(우), 2번 탭에 `implementer`(좌)와 `refiner`(우)를 배치합니다. 탭 내부 Pane은 좌우 분할(`--direction horizontal`)을 기본으로 합니다.

1. **2개 Tab 및 역할별 Pane 라벨·지정 모델 유지 의무**:
   * Orca 터미널 탭 2개에 4개 Pane을 나누어 활성화합니다. 한 화면에는 현재 선택한 탭의 Pane 2개만 표시합니다.
   * **Tab 1 — 감독·검토**: 좌 `supervisor`, 우 `reviewer`
   * **Tab 2 — 구현·보완**: 좌 `implementer`, 우 `refiner`
   * `supervisor`: 총괄 감독 (`claude` / **`Claude Opus 5.5`**, 기동 명령 `claude --model claude-opus-5-5`)
   * `implementer`: 메인 구현 (`opencode` / **`camelStream Auto`**, 기동 명령 `opencode -m camel-stream/auto`)
   * `reviewer`: 코드 검토 (`opencode` / **`Muse Spark 1.3 Contributor`**, 기동 명령 `opencode -m opencode-go/muse-spark-1.3-contributor`)
   * `refiner`: 보완 작업 (`opencode` / **`Muse Spark 1.3 Contributor`**, 기동 명령 `opencode -m opencode-go/muse-spark-1.3-contributor`)

2. **에이전트 기동 (Agent Start with Model)**:
   * `terminal create`로 탭을 만들고 `terminal split`으로 우측 Pane을 추가하며, 각 명령의 `--command`로 에이전트를 지정 모델과 함께 기동합니다. 각 명령의 JSON 결과에서 **터미널 핸들(`term_...`)을 기록**해 두고, 이후 모든 지시·조회는 이 핸들로 수행합니다.
   * `supervisor`가 이미 Orca 터미널에서 실행 중이면 1번 탭은 새로 만들지 않고, 현재 터미널 핸들(`orca terminal list --worktree active --json`로 확인)에 `reviewer`만 분할 추가합니다.
   ```bash
   # Tab 1 — supervisor(좌) + reviewer(우)
   orca terminal create --worktree active --title supervisor --command "claude --model claude-opus-5-5" --json
   orca terminal split --terminal <supervisor_handle> --direction horizontal --command "opencode -m opencode-go/muse-spark-1.3-contributor" --json

   # Tab 2 — implementer(좌) + refiner(우)
   orca terminal create --worktree active --title implementer --command "opencode -m camel-stream/auto" --json
   orca terminal split --terminal <implementer_handle> --direction horizontal --command "opencode -m opencode-go/muse-spark-1.3-contributor" --json

   # 역할 라벨 지정
   orca terminal rename --terminal <reviewer_handle> --title reviewer --json
   orca terminal rename --terminal <refiner_handle> --title refiner --json
   ```

3. **세션 시작 시 상태 검증 & 핸들 재매핑**:
   * Orca 터미널 핸들은 런타임 단위로 발급되므로 Orca 재시작 후나 `terminal_handle_stale` 오류가 나면 기존 핸들이 무효가 됩니다. 이때 `supervisor`는 가장 먼저 터미널 목록을 조회하여 4개 역할의 핸들을 다시 매핑하고, 이후에는 **새 핸들만** 사용합니다 (구 핸들과 새 핸들에 중복 전송 금지).
   * 에이전트가 실행 중 터미널 제목을 바꿀 수 있으므로, 제목이 역할명과 다르면 `terminal rename`으로 다시 지정합니다.


4. **모델 적용 및 화면 상태 최종 검증**:

## 🛠️ 4. Orca 협업 운영 명령어 가이드 (2-Tab / 4-Pane)

감독(`supervisor`)은 다음의 Orca CLI 명령어를 통해 각 에이전트와 통신하고 동기화를 제어합니다.

### 4.1 목표 중심 문서 포인터 지시 규약

프롬프트에는 핵심 과업과 목표를 간결하게 전달하고, 상세 스펙은 관련 위키 문서 경로를 지정하여 에이전트가 직접 정독하도록 합니다. 프롬프트에 긴 설계 내용을 복사하지 않으며, 표준 형식은 `[단계·핵심 목표] + [참조 위키 경로] + [산출물 경로]`로 구성합니다.

```bash
# 1. 2-Tab / 4-Pane 에이전트 연결 상태 점검
orca terminal list --worktree active --json

# 2. 지시 전 대상 에이전트가 입력 대기 상태인지 확인 (satisfied: true 일 때만 전송)
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000 --json

# 3. 특정 역할 Pane에 태스크 지시 (--wait-submit 으로 제출 확인)
orca terminal send --terminal <implementer_handle> --text "<implementer 작업 지시>" --enter --wait-submit 10 --json
orca terminal send --terminal <reviewer_handle> --text "<reviewer 검토 지시>" --enter --wait-submit 10 --json
orca terminal send --terminal <refiner_handle> --text "<refiner 보완 지시>" --enter --wait-submit 10 --json

# 4. 작업 완료 대기 (응답 결과의 wait.satisfied 확인, 시간 초과 시 재대기)
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 300000 --json

# 5. 에이전트의 작업 결과 및 보고서 읽기 (긴 출력은 nextCursor로 이어 읽기)
orca terminal read --terminal <handle> --limit 200 --json
orca terminal read --terminal <handle> --cursor <nextCursor> --limit 1000 --json
```

> [!NOTE]
> * `send` 결과의 `accepted: true`는 입력 수락만 의미합니다. 응답이 없다고 같은 지시를 재전송하지 말고, 전송 오류가 모호할 때만 결과에 표시된 `--retry-request <id>`로 동일 명령을 재시도합니다.
> * `wait`는 시간 초과 시에도 정상 결과를 출력하므로 반드시 `wait.satisfied` 값으로 완료 여부를 판단합니다.

## 💡 5. 사용자 제기 결함/문제점(User Feedback) 처리 규칙

에이전트의 자체 자동 분석이 아닌, **사용자(인간 개발자)가 실전 테스트 등을 통해 직접 발견하여 제기한 문제점**에 대해 분석, 보완 기획, 보완 작업을 수행할 때는 다음 규칙을 엄격히 적용합니다:

1. **기존 기능 범위 내 결함 및 버그 수정**:
   - 가장 최근에 완료/진행 중인 페이즈의 위키 사후 검토 보고서(`reviews/Talklite-Phase-X-사후검토.md`)에 `## [Round X] 사용자 제기 결함 분석 및 조치` 형태로 **내용을 하단에 누적 추가(Append-Only, 덮어쓰기 절대 금지)**하여 분석과 보완 내역을 영구 보존합니다.
2. **기능 확장 및 신규 파이프라인 도입인 경우**:
   - 단순 버그 수정이 아니라 해당 문제점 해결을 위해 **새로운 기능/도메인이 도입되거나 파이프라인이 확장되는 경우**(예: 독립 출력 장치 선택 파이프라인 도입 등)에는 기존 페이즈에 덧붙이지 않고 **별도의 독립 마일스톤(Phase X+1)으로 분리하여 정식 7단계 사이클로 수립 및 관리**합니다.
